# 결정 기록

결정마다 "선택한 것, 버린 것, 해결한 것, 남은 것, 새로 생긴 문제"를 남깁니다. 새 결정은 아래에 추가하고, 결정을 뒤집을 때는 지우지 말고 "뒤집음" 항목을 새로 씁니다.

---

## 1. 코드 구조: 단일 모듈, 흐름 단계별 패키지

- **선택한 것**: Java 21, Gradle 단일 모듈. 패키지를 `serving/`, `event/`, `billing/`, `reconcile/`처럼 광고 한 건이 흐르는 단계로 나눔. 옥션과 과금 판정 같은 규칙은 스프링 없는 순수 클래스로 분리. DB 접근은 `JdbcTemplate`.
- **버린 것**: PAM의 Kotlin 멀티 모듈 클린 아키텍처(api, application, domain, infrastructure). 모듈 경계를 지키는 인터페이스와 어댑터 때문에 "클릭 한 건이 어떻게 과금되나"를 따라가려면 네 모듈을 오가야 함. 이 저장소의 목표는 사용자가 코드를 읽고 설명하는 것이고, 기한은 약 4일.
  JPA도 버림. 과금의 핵심인 "유니크 INSERT + 예산 UPDATE를 한 트랜잭션으로"가 flush 시점 뒤에 숨어 보이지 않음.
- **해결한 것**: 한 단계의 코드가 한 폴더에 모임. 규칙 클래스가 DB를 모르므로 CLAUDE.md 4장의 기본 예시 표(c1~c7)를 DB 없이 단위 테스트로 돌릴 수 있음. SQL이 코드에 그대로 보여 면접에서 쿼리 단위로 설명할 수 있음.
- **남은 것**: 패키지 사이 의존 방향을 컴파일러가 막아주지 않음(멀티 모듈이었다면 막힘). `billing/`이 `serving/`을 직접 부르는 식의 엉킴은 리뷰로 막음.
- **새로 생긴 문제**: SQL을 손으로 쓰므로 컬럼 이름 변경 같은 실수를 컴파일 단계에서 못 잡음. 저장소 계층 테스트를 compose의 실제 Postgres로 돌려서 보완.

## 2. 배포 시점: 0단계에서 먼저 올림

- **선택한 것**: 기능보다 먼저 빈 뼈대(`/actuator/health`)를 PAM 서버에 올리고, 이후 단계는 main 머지마다 자동 배포.
- **버린 것**: "로컬에서 다 만들고 마지막에 배포". 처음 문서의 계획이었음.
- **해결한 것**: 1GB 메모리, ARM 아키텍처, 원격 저장소 지연 같은 서버 쪽 문제를 마지막 날이 아니라 첫날 만남. 단계마다 "서버에서 동작"을 완료 기준으로 쓸 수 있음.
- **남은 것**: 첫 배포 전 준비(시크릿 등록, Neon 데이터베이스 생성, PAM 컨테이너 정지)를 사용자가 해야 함. `docs/pam-infra.md` 5-7.
- **새로 생긴 문제**: 서버(춘천)와 Neon, Upstash(싱가포르)가 리전이 달라, 서빙 경로의 50ms 예산을 원격 저장소 왕복만으로 넘길 수 있음. 0단계에서 측정한 뒤 서빙 설계(메모리 캐시 여부)를 정함. `docs/pam-infra.md` 5-6.

## 3. 도메인: PAM API 서브도메인을 이어 씀

- **선택한 것**: PAM 백엔드가 쓰던 API 서브도메인을 그대로 씀.
- **버린 것**: 새 서브도메인. DNS, Nginx, 인증서 세 곳을 새로 설정해야 함.
- **해결한 것**: 서버 쪽 설정 변경 없이 컨테이너만 바꾸면 됨(호스트 8080 포트 유지).
- **남은 것**: PAM 프론트엔드는 계속 떠 있지만 API가 바뀌므로 기능이 동작하지 않음. 서버만 내린다는 결정에 따라 그대로 둠.
- **새로 생긴 문제**: 없음.

## 4. 이미지 빌드와 배포 방식 (0단계)

- **선택한 것**: jar는 GitHub Actions 러너에서 `./gradlew bootJar`로 만들고, Dockerfile은 그 jar를 JRE 이미지에 복사만 함. 이미지는 amd64, arm64 둘 다 만들어 GHCR에 `latest`와 커밋 SHA 태그로 push. 서버에는 SHA 태그로 배포.
- **버린 것**: PAM처럼 Dockerfile 안에서 빌드하는 2단계 구성. 서버 아키텍처가 확인되지 않아(`docs/pam-infra.md` 5-3) arm64도 만들어야 하는데, x86 러너에서 arm64 Gradle 빌드를 에뮬레이션(QEMU)으로 돌리면 매우 느림.
- **해결한 것**: 서버가 어느 아키텍처든 맞는 이미지가 받아짐. Dockerfile에 RUN이 없어 arm64 빌드도 빠름. 테스트를 통과한 바로 그 jar가 이미지에 들어감. 어떤 커밋이 떠 있는지 태그로 알 수 있음.
- **남은 것**: GHCR 오래된 이미지 정리 작업을 넣지 않음. 여러 아키텍처 이미지는 아키텍처별 하위 이미지가 태그 없이 저장되는데, PAM 방식의 정리 작업(`delete-package-versions`)이 이것을 지워 최신 이미지를 깨뜨릴 수 있음. 첫 배포 로그의 `uname -m`으로 아키텍처를 확인한 뒤 한 아키텍처로 줄이고 정리 작업을 추가함.
- **새로 생긴 문제**: 로컬에서 `docker compose up`으로 앱 컨테이너를 띄우려면 먼저 `./gradlew bootJar`를 해야 함(README에 적음).

## 5. 서버 ↔ 원격 저장소 왕복 시간은 기동 로그로 잰다 (0단계)

- **선택한 것**: 앱 기동 직후 Postgres `SELECT 1`, Redis `PING`을 각각 23번(앞 3번 버림) 보내 min, p50, p95, max를 로그에 남김(`common/LatencyProbe`). 배포 워크플로가 이 로그를 출력.
- **버린 것**: 측정용 HTTP 엔드포인트. 밖에서 반복 호출되면 Upstash 명령 수, Neon 사용량이 늘어남.
- **해결한 것**: 서버에 접속하지 않고 GitHub Actions 로그에서 숫자를 볼 수 있음. 로컬 측정값(Postgres p50 0.2ms, Redis p50 0.4ms)과 바로 비교 가능.
- **남은 것**: 서버 측정값은 첫 배포 후 이 항목 아래에 추가하고, 그 숫자로 1단계 서빙 설계(매 요청 원격 조회 vs 메모리 캐시)를 정함.
- **새로 생긴 문제**: 기동할 때마다 Upstash 명령이 약 25개 나감. 배포 횟수 수준이라 무시할 만함.

## 6. 범위를 광고 흐름 순서로 다시 짬

- **선택한 것**: 범위를 광고 한 건의 흐름(서빙 → 측정 → 전환 → 과금 → 대사, 성과) 순서로 다시 짬. 서빙에 사용자 신호 보정, 플랫폼 가중치, 최저가, 블렌딩, 피로도 상한, 채움률, 서킷 브레이커를 넣음. 측정에 데모 페이지(렌더링, viewable 노출, sendBeacon 비교, 파라미터 체이닝)와 GIVT 필터를, 새 단계로 전환과 ROAS를 넣음.
- **버린 것**: "과금 컨슈머가 가장 중요하니 과금을 깊게" 하는 원래 무게 배분. 지금 최우선은 광고 도메인을 흐름 전체로 체계적으로 경험하는 것이고, ROAS, viewable, 클라이언트 쪽 유실처럼 과금만 깊게 파서는 만날 수 없는 개념이 많음.
- **해결한 것**: CLAUDE.md 3장(3-12, 3-13 추가)의 개념이 모두 "어디서 만져 보나" 또는 "왜 하지 않나"에 연결됨(README 개념 표). 브라우저에서만 생기는 문제를 데모 페이지로 직접 볼 수 있음.
- **남은 것**: 기한 안에 다 못 하면 과금 단계의 대조 실험, 늦은 도착, 초과 집행 측정을 설명과 남은 한계로 대신함. 그때 이 아래에 기록.
- **새로 생긴 문제**: 데모 페이지라는 프론트엔드 조각이 생김. 측정 장치로만 쓰고 매체 프론트엔드처럼 키우지 않음(정적 HTML, 프레임워크 없음). 사용자 신호를 어디에 둘지는 1단계에서 정함(7번).

## 7. 서빙은 메모리 스냅샷 + 요청당 Redis 한 번 (1단계)

- **선택한 것**: 모든 사용자에게 같은 데이터(광고, 일반 상품, 소진 표시)는 5초마다 메모리 스냅샷으로 새로 읽고(`Catalog`), 사용자마다 다른 데이터(최근 본 브랜드, 광고별 노출 횟수)만 요청마다 Redis `MGET` 한 번으로 읽음(`UserSignals`). 광고 고르기 전체에 50ms 시간 제한.
- **버린 것**: 요청마다 DB에서 후보를 조회하는 방식. 서버(춘천)와 Neon(싱가포르) 왕복만으로 50ms를 다 쓸 수 있음. 키마다 Redis를 따로 부르는 방식도 버림(후보 수만큼 왕복이 늘어남).
- **해결한 것**: 서빙 한 번의 원격 왕복이 Redis 한 번으로 고정됨. DB나 Redis가 잠깐 죽어도 스냅샷으로 계속 서빙(새로 읽기 실패 시 이전 스냅샷 유지).
- **남은 것**: 서버의 Upstash 왕복 시간이 50ms에 가까우면 Redis 한 번도 부담. 0단계 배포 로그의 숫자로 판단하고, 넘으면 사용자 신호도 비동기로 미리 올리는 방식을 검토.
- **새로 생긴 문제**: 스냅샷 주기(5초)만큼 예산 소진 반영이 늦음. 그 사이 나간 광고의 클릭이 초과 집행이 됨(4단계 시나리오에서 측정).

## 8. 개인화 신호는 최근 본 브랜드 (1단계)

- **선택한 것**: 최근 본 브랜드와 광고 상품 브랜드가 같으면 pCTR을 2배로 보정.
- **버린 것**: 처음 계획한 "최근 본 카테고리". 서빙 요청 자체가 카테고리 페이지(`category=shoes`)라 후보가 이미 같은 카테고리로 걸러져, 카테고리 신호로는 광고끼리 차이가 생기지 않음.
- **해결한 것**: 같은 페이지, 같은 광고들인데 사용자에 따라 1등이 바뀌는 장면을 만들 수 있음(runway를 본 사용자 → runway 1등).
- **남은 것**: 신호를 남기는 쪽은 지금 `POST /signals/viewed-brand`를 직접 부름. 2단계 데모 페이지에서 상품 상세를 열 때 자동으로 남기게 함.
- **새로 생긴 문제**: 없음.

## 9. 노출 토큰은 저장하지 않고 서명만 (1단계)

- **선택한 것**: 토큰 = base64url(고유 ID|광고 ID|사용자 ID|낙찰 CPC|발급 시각) + "." + HMAC-SHA256 서명. 서버는 저장하지 않고 이벤트가 올 때 서명만 확인.
- **버린 것**: 서빙 때 토큰을 DB나 Redis에 저장하고 이벤트 때 조회하는 방식. 서빙 경로에 쓰기가 하나 더 생겨 50ms 예산을 씀.
- **해결한 것**: 클릭이 들어오면 과금액을 클라이언트 값이 아니라 옥션이 정한 값(토큰 안의 CPC)으로 씀. 위조된 CPC, 없는 광고의 클릭을 막음.
- **남은 것**: 토큰 만료 시간이 없음. 오래된 토큰의 클릭을 어떻게 볼지는 2단계에서 정함. 비밀키는 서버의 `TOKEN_SECRET`으로 바꿔야 함.
- **새로 생긴 문제**: 토큰 내용은 서명만 되고 암호화되지 않아 누구나 읽을 수 있음(광고 ID, 낙찰가). 학습용으로는 오히려 읽을 수 있는 편이 낫다고 보고 그대로 둠.

## 10. 노출 수집: 중복 확인, 피로도, 스트림 적재를 Lua 하나로 (2단계)

- **선택한 것**: 이벤트 한 건의 처리(같은 이벤트인지 `SET NX`, 렌더링이면 피로도 `INCR`과 첫 회 `EXPIRE`, 파티션 스트림 `XADD`, 건수 `INCR`)를 Lua 스크립트 하나로 원자 처리(`scripts/collect_event.lua`).
- **버린 것**: 명령을 하나씩 보내는 방식. 사이에 앱이 죽으면 "중복 표시는 됐는데 스트림에는 없는" 노출이 생겨 재전송이 와도 영원히 못 받음. PAM 요청 제한이 같은 이유로 Lua로 바꿨음.
- **해결한 것**: 재전송은 정확히 한 번만 셈. 노출 한 건이 Redis 왕복 한 번.
- **남은 것**: 피로도 창은 첫 노출부터 1시간인 고정 창이라, 창 경계 직전과 직후에 몰아서 보면 1시간 안에 상한의 2배까지 볼 수 있음. 미끄러지는 창(sorted set)은 더 정확하지만 복잡해서 미룸.
- **새로 생긴 문제**: 중복 확인 키가 노출마다 하루씩 남아 Redis 메모리를 씀. 학습용 트래픽에서는 무시할 수준.

## 11. 클릭은 수집 단계에서 중복 제거하지 않음 (2단계)

- **선택한 것**: 클릭은 clickId만 붙여 그대로 스트림에 넣고(최소 한 번 전달), 중복 판정은 4단계 과금 컨슈머의 장부(click_id 유니크)에 맡김.
- **버린 것**: 노출처럼 입구에서 `SET NX`로 거르기. 입구에서 "받았다"고 표시한 뒤 과금 전에 죽으면, 재전송이 와도 입구에서 막혀 그 클릭은 과금되지 않음.
- **해결한 것**: "결과를 확정한 곳에서만 중복을 판정한다"(CLAUDE.md 3-11)를 지킴. 돈이 걸린 판정은 한 트랜잭션 안에서 한 번.
- **남은 것**: 클릭 URL 방식(리다이렉트)은 서버가 clickId를 새로 만들어, 사용자가 뒤로 가기 후 다시 누르면 다른 클릭이 됨. 이건 재전송이 아니라 실제 재클릭이라 맞는 동작이고, 10초 규칙이 연타를 막음.
- **새로 생긴 문제**: 스트림에는 중복 클릭이 남아 있어, 스트림 길이를 클릭 수로 읽으면 안 됨(대사는 장부 기준).

## 12. 클릭을 보내는 방법 세 가지를 데모에 나란히 둠 (2단계)

- **선택한 것**: 클릭 URL(서버 리다이렉트), sendBeacon, fetch(모아서 150ms 뒤 전송)를 토글로 비교. 기본값은 클릭 URL.
- **버린 것**: 한 방식만 구현. 차이를 직접 보는 것이 목적이라 일부러 나쁜 방식(fetch)도 둠.
- **해결한 것**: 실측으로 fetch 3번 → 서버 0건, sendBeacon 3번 → 3건, 클릭 URL 1번 → 1건. "브라우저 보냄 vs 서버 도착" 표로 클라이언트-서버 대사를 체험.
- **남은 것**: 클릭 URL은 가장 확실하지만 이동 전에 서버를 한 번 거쳐 페이지가 조금 늦게 뜨고, `/events/click` 같은 경로는 광고 차단 목록에 걸리기 쉬움. sendBeacon은 빠르지만 응답을 확인할 수 없고 크기 제한(약 64KB)이 있음.
- **새로 생긴 문제**: fetch 모드의 150ms 지연은 SDK 일괄 전송을 흉내 낸 것이라, 지연 없는 fetch는 환경에 따라 도착하기도 함. 문서에 그렇게 적음.

## 13. 도식은 Archify로, 설치 없이 고정 버전을 세션마다 받아 씀

- **선택한 것**: 설명용 도식은 Archify 에이전트 스킬(v3.2.0, Apache-2.0)로 만든 인터랙티브 HTML로 둠. 스킬은 저장소에 넣지 않고 세션마다 임시 폴더에 `git clone --branch v3.2.0`으로 받아 씀. 업데이트 확인 요청은 `ARCHIFY_UPDATE_CHECK_DISABLED=1`로 끔. 원본 JSON(`docs/diagrams/src/`)과 결과 HTML만 커밋.
- **버린 것**: 저장소 안 설치(외부 스킬 파일 약 18MB가 학습 코드와 섞임), 전역 설치(클라우드 컨테이너라 세션이 끝나면 사라짐), Mermaid만 쓰기(GitHub에서 바로 보이지만 경로 강조, 단계별 따라가기 같은 탐색이 안 됨).
- **해결한 것**: 저장소에는 학습 코드와 그 도식만 남음. 원본 JSON을 고쳐 다시 만들 수 있어 코드가 바뀌면 도식도 같이 고칠 수 있음.
- **남은 것**: 세션마다 받는 시간(수십 초)이 듦. 외부 코드를 실행하므로 작업 환경의 권한 승인이 필요할 수 있음.
- **새로 생긴 문제**: 결과 HTML은 GitHub 화면에서 그림으로 보이지 않음. 파일을 받아 브라우저로 열어야 함.

## 14. 어트리뷰션: 마지막 클릭, 7일, 같은 상품, 두 경로로 구매자 찾기 (3단계)

- **선택한 것**: 같은 상품 광고의 클릭 중 구매 전 7일 안의 마지막 클릭에 귀속(`Attribution`). 구매자는 URL 토큰 안의 사용자 ID(TOKEN 경로) 또는 로그인 사용자 ID(USER_HISTORY 경로)로 찾고, 클릭 기록은 2단계 수집이 남긴 `ads:clicks:{사용자}`(Redis 정렬 집합, 8일 유지)를 읽음.
- **버린 것**: URL 토큰만으로 귀속(처음 계획). 일반 웹 광고처럼 체이닝이 끊기면 끝나서, 리테일 미디어의 가장 큰 차이인 클로즈드 루프를 보여줄 수 없음. 멀티 터치(여러 광고에 나눠 귀속), view-through(클릭 없는 노출 후 구매), 할로 효과(같은 브랜드 다른 상품)도 버림. 규칙이 하나여야 설명하고 검증할 수 있음.
- **해결한 것**: 체이닝 단절이 "로그인이면 복구, 비로그인이면 유실"로 나뉘는 장면을 데모에서 직접 봄. 같은 주문은 기본 키로 한 번만.
- **남은 것**: 클릭 기록이 Redis에만 있어 Redis를 잃으면 7일치 귀속 근거가 사라짐(4단계 장부가 생기면 장부에서 다시 찾을 수 있음). 구매 취소, 반품을 반영하지 않음(정산은 구매 확정 후라는 3-7 원칙은 설명만).
- **새로 생긴 문제**: 로그인 사용자의 클릭 기록으로 귀속하면, URL 토큰이 가리키는 클릭보다 더 최근의 다른 클릭이 이길 수 있음(마지막 클릭 규칙이라 의도대로). 응답의 경로(TOKEN/USER_HISTORY)로 구분해 보여줌.

## 15. 3단계 ROAS는 추정 광고비로 (3단계)

- **선택한 것**: 클릭 수집 때 처음 보는 clickId면 광고별 `ads:est-spend:{광고}`에 낙찰 CPC를 더하고(Lua 안에서 `ZADD` 결과로 판정), `/conversions/stats`에서 귀속 매출 ÷ 추정 광고비로 추정 ROAS를 냄.
- **버린 것**: 4단계 과금 장부를 기다렸다가 ROAS를 계산. 3단계의 핵심 장면(체이닝 단절이 ROAS를 깎음)을 바로 숫자로 보여줄 수 없음.
- **해결한 것**: 재전송 클릭은 추정 광고비에 두 번 들어가지 않음. 체이닝 단절 한 번으로 ROAS가 217배 → 145배가 되는 것을 실측.
- **남은 것**: 10초 규칙, 예산 부족 같은 과금 규칙을 적용하기 전 값이라 실제 광고비보다 큼. 5단계에서 장부의 실제 광고비와 나란히 두고 차이(= 과금하지 않은 클릭)를 보여줌.
- **새로 생긴 문제**: "추정"과 "실제" 두 ROAS가 생겨 헷갈릴 수 있음. 응답 필드 이름을 `estimatedSpend`, `estimatedRoas`로 분명히 함.

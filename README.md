# 미니 광고 서버

커머스 상품 광고(CPC)를 서빙하고, 노출과 클릭을 수집하고, 클릭마다 과금하고, 그 결과가 서로 맞는지 대사하는 학습용 광고 서버입니다.
배경 지식과 작업 원칙은 [CLAUDE.md](./CLAUDE.md), 용어는 [docs/keywords.md](./docs/keywords.md), 결정 기록은 [docs/tradeoffs.md](./docs/tradeoffs.md)에 있습니다.

## 전체 흐름

광고 한 건은 두 갈래 경로를 지납니다. **서빙 경로는 빨라야 하고, 측정 경로는 정확해야 합니다.**

```
[서빙 경로: 동기, 50ms 예산]                         패키지
  매체 페이지 ── GET /ads?slot&category ──▶ 광고 서버          serving/
     ① 후보 추리기  카테고리 일치, 예산 남음, 소진 표시 없음
     ② 랭킹        eCPM = 입찰가 × pCTR × 1000
     ③ 옥션        2등가: 낙찰 CPC = 2등 eCPM ÷ (내 pCTR × 1000) + 10원
     ④ 응답        광고 + 노출 토큰(서명된 고유 ID, 광고 ID, 낙찰 CPC, 발급 시각)
     50ms를 넘기면 광고 없이 응답(페이지가 광고 때문에 느려지면 안 됨)

[측정 경로: 비동기, 늦어도 되지만 잃거나 두 번 세면 안 됨]
  화면에 그려짐 ── POST /events/impression {token} ─┐            event/
  사용자 클릭   ── GET  /events/click?token ────────┤ 토큰 검증
                  (원래 상품 페이지로 리다이렉트)      ▼
                              Redis Streams: hash(adId) % 4 개 스트림(파티션 흉내)
                                                   │
                                                   ▼
                  과금 컨슈머(파티션마다 하나)                     billing/
                    재전송? → 부정 클릭(10초)? → 예산 부족? → 과금
                    장부 INSERT(click_id 유니크) + 예산 UPDATE = 한 트랜잭션
                    커밋 후 ACK / 소진되면 Redis에 소진 표시 ─▶ 서빙 ①이 읽음
                                                   │
                                                   ▼
                  대사 배치: 클릭 수 = 과금 + 무과금(사유별)       reconcile/
                            장부 합계 = 광고별 예산 차감액
```

## 개념이 어디에 구현되나

CLAUDE.md 3장의 개념을 전부 이 표에 올립니다. "설명만"인 개념도 왜 구현하지 않는지 적어, 면접에서 "그건 어떻게 하나요?"에 답할 근거로 씁니다.

| 개념 (CLAUDE.md) | 구현 위치 | 상태 |
|---|---|---|
| 지면(슬롯), 맥락 타게팅(카테고리) (3-1, 3-2) | 1단계 `serving/` 후보 필터 | 예정 |
| pCTR, eCPM 랭킹 (3-3) | 1단계 `serving/` (pCTR은 광고별 고정값) | 예정 |
| 2등가 옥션 (3-4) | 1단계 `serving/` | 예정 |
| 노출 토큰, "모든 이벤트는 서빙 결정에 묶인다" (3-2) | 1단계 발급, 2단계 검증 | 예정 |
| 서빙 시간 예산, 광고 없이 응답 (3-2) | 1단계 50ms 타임아웃 | 예정 |
| 원격 저장소 왕복 시간 | 0단계 `common/LatencyProbe` | 완료 |
| 노출의 정의(렌더링 시작) (3-6) | 2단계 노출 이벤트 | 예정 |
| 최소 한 번 전달, 고유 ID로 중복 제거 (3-6, 3-10) | 2단계 적재, 3단계 click_id 유니크 | 예정 |
| 파티션 키, 단일 처리 (3-10) | 2·3단계 `hash(adId) % 4` | 예정 |
| CPC 과금, 멱등성, 부정 클릭 기본 방어(IVT) (3-8, 3-11) | 3단계 `billing/` | 예정 |
| 예산 소진, 초과 집행 (3-5) | 3단계 + 시나리오 테스트 | 예정 |
| 이벤트 시간과 처리 시간, 늦게 온 이벤트 (3-10) | 3단계 시나리오 테스트 | 예정 |
| 대사, 원장 (3-9) | 4단계 `reconcile/` | 예정 |
| 최저가(reserve price) (3-4) | 옥션에 하한 하나 추가하면 됨 | 추가 후보 |
| 채움률(fill rate), 서킷 브레이커 (3-2) | 서빙 결과 집계, 연속 타임아웃 시 차단 | 추가 후보 |
| CTR과 노출 유실 왜곡 (3-3) | 대사 리포트에 광고별 CTR 추가 | 추가 후보 |
| 뷰어빌리티(50% 1초) (3-6) | 클라이언트 측정이 필요. 서버는 "본 노출" 플래그만 받을 수 있음 | 추가 후보 |
| 예산 집행 속도 조절(pacing) (3-5) | 시간대별 목표 소진 곡선 대비 확률적 참여 | 추가 후보 |
| 전환, CVR, ROAS, 어트리뷰션 윈도우 (3-3, 3-7) | 구매 이벤트와 노출 토큰 연결 | 추가 후보 |
| 핫 파티션 (3-10) | 키 쪼개기는 예산 분할이 필요해 설명만 | 설명만 |
| Affiliate (3-7) | 광고 서버가 아닌 별도 정산 흐름 | 설명만 |
| DSP, SSP, RTB/OpenRTB (3-1) | 이 서버는 자기 지면에 자기 광고를 내는 리테일 미디어 구조라 외부 경매가 없음 | 설명만 |
| 장기 정산 워크플로(Temporal) (3-9) | 한 DB 안에서 끝나는 클릭 과금에는 불필요 | 설명만 |

## 실행

필요한 것: JDK 21, Docker.

```bash
# 저장소(Postgres, Redis)만 띄우고 앱은 Gradle로
docker compose up -d postgres redis
./gradlew bootRun

# 테스트 (compose의 Postgres, Redis가 떠 있어야 함)
./gradlew test

# 앱까지 전부 컨테이너로
./gradlew bootJar && docker compose up --build
```

확인: `curl localhost:8080/actuator/health` → `{"status":"UP"}`

## 배포

main에 머지하면 GitHub Actions가 테스트 → 이미지 push(GHCR) → 서버 배포 → 헬스체크까지 합니다(`.github/workflows/deploy.yml`).
배포 로그 마지막에 서버 ↔ DB, Redis 왕복 시간(`[latency]`), 컨테이너 메모리, 서버 CPU 아키텍처가 찍힙니다.
서버 준비와 구성은 [docs/pam-infra.md](./docs/pam-infra.md) 5장에 있습니다.
